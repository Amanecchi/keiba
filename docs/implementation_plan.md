## 開発順序の最新指定

確認フォームへの回答により、機能1の初版はJRA平地重賞全体・最低10年以上、ご本人だけがログインして利用、Webサーバー・DB・原本/バックアップ等の運用費も無料に限定する。有料化や自動課金を解決策にせず、無料枠の容量・通信・CPU・ジョブ上限と超過時の停止を検証する。

**機能1：過去データの条件別分析・表示**を単独のWeb機能として完成させ、ユーザーの完成確認を得てから、**機能2：その分析を今回の出走馬へ適用する機能**を開発する。最終版では両機能を同時に参照・連携して使えるようにする。

機能1は今回のレース・出馬表・発売中オッズを選択しなくても完結する。合意した対象範囲の最低10年以上の履歴収集とWeb上の受け入れ確認を機能1の区切りより前へ移した。現在の代表取得・83件のテストは開発成果であり、機能1の完成確認ではない。

## 1. データ取得元と取得範囲を調査する

成果物：docs/data_source_research.md、docs/data_source_options.md、docs/jra_official_formats.md、docs/acquisition_probe.md、自動取得検証CLI・テスト、項目対応表、取得範囲一覧、確認証跡。選択後の原本は作業用に保存。

完了条件：無料候補の項目・期間・制約・全体コストを比較し、ユーザーが選択できる。機能1に必要な過去の原本と項目を自動取得でき、その負担を少量検証する。次走の出馬表・単複の既存実証は保持するが、その発売状態を機能1の稼働条件にしない。環境制限などの残件を取得済みとしない。必要な過去取得が成立しなければ方式比較へ戻る。

## 3. Web配備構成を選び、Web画面・APIの基盤を作る

作業：無料配備候補、対応ランタイム・ジョブ時間・永続容量・転送量と超過時の停止を比較する。既存Pythonを再利用するWeb画面・分析API・取得ワーカーの構成を選ぶ。検証用URL、本人限定ログイン、サーバー設定、依存固定、ログ、テストを整備する。配備候補からJRAのHTTPS・フォーム送信も少量検証する。調査は作業2と並行できる。有料契約や超過課金は採用しない。

## 4. DBと原本・履歴の保存基盤を作る

## 5. 代表レースの取得と再開可能な取り込みを作る

成果物：サーバー取得ワーカー、ジョブ登録・状態取得API、解析器、保存済みサンプルによるテスト、取得結果報告。
