## 1. 当時所属は、結果の調教師と所属歴から補完できる

PC版の結果や最終オッズには所属がなかったが、公式の調教師情報ページに「所属歴」が存在した。例えば「2001年から 栗東T・C」のように、年と所属先が明示される。

結果の管理調教師リンクから6桁IDを取得し、所属歴ページ内の本年・重賞成績等のメニューに含まれるIDとも照合する。そのIDの年付き所属歴と対象レースの年から所属先を決め、証拠の期間・免許年・原本URL・ハッシュを出走へ保存する。馬の現在の調教師や、調教師の現在所属だけから逆算しない。

年しか示されない移動年に美浦・栗東の両方が候補になる場合は不明とする。範囲外や形式不明も補完しない。今回1件あった最初の所属年とレース年の一致は、免許取得年も一致し、そのIDが公式結果で管理調教師として確認できたため、初免許年の所属として解決した。これは異なる所属間の移動年を推測する規則ではない。

2016〜2025年のアルゼンチン共和国杯10開催について、159出走（129頭）の所属が159件揃った。内訳は栗東93・美浦66。81件の異なる公式調教師ページを使用した。同一調教師のページは開催・馬をまたいで再利用できる。

| 実行 | 新規HTTP | キャッシュ利用 | 受信量 | 経過時間 |
| --- | ---: | ---: | ---: | ---: |
| 保存済み過去原本へ所属歴を追加 | 81 | 284 | 5,426,856 bytes | 190.3964秒 |
| 境界年の規則を確定後、全頭を再解析 | 0 | 365 | 0 bytes | 74.8177秒 |

最初の実行は158件、再解析後に159件。最終確認では不足・解析エラーがなく、結果10・最終オッズ10・馬プロフィール159出走分・所属歴146参照を再現した。異なる原本261件のSHA-256と、159出走の調教師ID・所属歴・採用値の対応を再検査した。81ページの所属歴全件をリポジトリへ転載していない。

```bash
.venv/bin/python -m keiba_acquisition.cli --database --trainer-history \
  --years 2016:2025 --profiles-per-race 18 --output work/acquisition-ten-years
```

`--trainer-history` は追加検証を明示するオプション。省略すれば従来の取得範囲を維持する。

## 2. 枠・馬番公開後の出馬表と発売中単複

2026-11-08東京11Rの出馬表18頭について、枠・馬番・馬ID・騎手・種牡馬・所属を取得した。公開後の馬名欄には、単勝オッズ・人気・賞金・馬主・血統等をまとめた別の見出しが使われていたため、この観測した形式に対応した。馬名へ他の情報を混ぜず、埋め込まれた単勝と人気も別の値として読む。

単複オッズは注意書きに「最終オッズ」という語があるだけで最終値と判定されていた。更新欄の状態ラベルを優先して読むよう修正し、発売中の値を正しく区別した。出馬表とオッズの開催キーだけでなく、全馬の馬番・馬ID集合も検査する。

`--current-only` により、過去レースを取得せず今回のデータだけを実行できる。公開前・未発売・別開催・馬ID不一致・最終値の混入では合格にしない。

```bash
.venv/bin/python -m keiba_acquisition.cli --current-only \
  --upcoming-url 'https://www.jra.go.jp/keiba/race/101/syutsuba.html' \
  --output work/live-20261107
```

同じ保存先へ2回実行し、双方で18頭の単勝・複勝上下限と馬IDが揃った。提供時刻は**14時09分現在 → 14時11分現在**へ進み、18頭中15頭の単勝または複勝上下限が変わった。各回は3 HTTP・約403KB・約4.5秒。これは発売中の実データであり、前回の未発表画面や過去の最終値を使った確認ではない。

提供時刻の原文とUTCの取得日時を別々に記録した。原文には日付がないため、アプリで日跨ぎ時の提供日付を決める規則は未確定。今回の観測と、任意の日時に使える鮮度判定の完成を区別する。

## 3. 更新前の原本・抽出結果を保持する

旧方式は同じURLの再取得で原本を置換し、抽出JSONも同じパスへ書き込んでいた。更新前後の証拠を残すため、v0.3.0から以下に変更した。

- HTTP応答ごとに `raw/<URL・メソッドのキー>/<UTC時刻>-<本文ハッシュ>.html` と対応JSONを保存する。
- 最新版の参照だけを `cache/<キー>.json` で更新する。キャッシュはURL・メソッド・保存先・ハッシュを検査する。
- 抽出JSONも実行ID・取得イベントごとのパスに保存し、過去のレポートが当時の原本・抽出結果を参照し続ける。
- 新規取得が失敗しても以前の成功原本と索引を維持する。旧形式の履歴原本・メタデータは読み込め、更新しても旧ファイルを置換しない。

実際の2回の現在取得で、両方の原本と抽出JSONを読み直し、各レポートのハッシュ・取得時刻・保存先の対応を確認した。11/5の現在情報の一部は変更前の再取得で既に置換されており、版別保存開始前の失われた本文を復元したという意味ではない。過去10開催の保存原本は今回も再利用できた。
