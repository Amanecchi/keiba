# Webシステムとしての構成・配備方針

版：0.6 / 更新：2026-11-08 / 状態：過去分析Web本体は内部検証。環境外保存は保持。DB適合性の実証完了まで追加収集は停止。

**構成見直し：将来の未勝利戦等への拡張を含め、原本・JSON一体保存とPython全件読込は最終構成として不採用。** 検索用SQL列・索引・SQL集計・サーバー側ページ送りと、原本/旧版の非公開ファイル保存へ分離する。[DB評価](database_feasibility.md) を優先する。以下のv0.5.x保存仕様は既存実装の記録であり、配備先と容量を採用確定したものではない。

## 1. 作成するもの

別々の目的を持つ2機能のWebシステムを作る。まず**機能1：過去データを条件別に分析・表示する機能**を独立して完成させる。ユーザーの完成確認後に、**機能2：機能1の分析を今回の出走馬へ適用する機能**を追加する。最終版では両方を同時に確認・連携して使えるようにする。

機能1ではレース・期間・条件を直接指定でき、今回のレース、出馬表、発売中オッズがなくても操作を完結できる。機能2はその条件と分析結果を参照し、今回の各馬の一致状況と単複の期待値の目安を表示する。

利用者はURLへアクセスし、ブラウザで条件選択・比較・更新を行う。JRAからの取得、データ保存、検索・計算はサーバーで実行する。PCへのPython導入、取得コマンド実行、DB起動を利用条件にしない。

| 画面 | 利用者が行うこと | 表示するもの |
| --- | --- | --- |
| 過去の傾向 | レース・期間・条件を指定し、分類別に比較 | 該当出走、勝率・連対率・3着以内率・複勝的中率・実績回収率、分母と根拠明細 |
| 今回の出走馬 | 対象レースを選び、出馬表・オッズを更新して同じ条件を照合 | 一致・不一致・不明、過去の率と分母、単複オッズと時刻、期待払戻・期待収支・回収率の目安 |
| データ管理 | 期間・区分を選び、取得・再実行・状況確認 | ジョブ進捗、欠損・未対応・更新失敗、取得範囲、バックアップの状態 |

条件は枠・脚質・騎手・種牡馬・性齢・所属・前走クラス/距離/間隔/名前/着順・人気・単勝帯等。AND/項目内OR、未知値、情報時点、期待値の式は [基本設計](basic_design.md) と [分析規則草案](analysis_rules.md) を維持する。対象は最低10年間の重賞履歴を起点とし、区分の対応を明示する。

## 3. 論理構成と第一候補

v0.5.1で、開発環境消失への備えとして環境外の本人限定Sites/D1を作成・配備した。Python取得器の `MirroredStore` が原本・解析版・進捗を同期し、受領確認なしに次の取得を続けない。既存のChatGPT認証で作成でき、DB保存のために新たなRender/Neonアカウントを要求する必要はなくなった。作業用PostgreSQLは実行環境内にもあるが、データは独立したD1にも保存される。[具体手順](acquisition_pipeline.md)、[環境外保存・復元検証](research/storage/2026-11-07/report.md) を参照。

保管庫はデータ保護用の稼働コンポーネント。分析画面/APIを含む最終Web構成は、既存Python実装を維持しつつ無料条件・全対象容量・操作性を検証して仕上げる。現在のSites利用枠と将来の料金/上限は別途確認し、長期無料運用を未実証のまま断言しない。以下のRender/Neon案は既存の比較履歴として保持する。

```text
ブラウザ → HTTPSのWeb画面 → 分析・検索API → 永続DB
                              ↓ 取得ジョブ登録
                         Python取得ワーカー → JRA公式
                              ↓
                         永続的な原本保存 → 解析・検査 → DB
```

v0.5.0はFlaskで画面/API、SQLAlchemyでPostgreSQLへの保存を実装。Gunicornは1ワーカー・4スレッド、取得は1ジョブずつのバックグラウンドスレッドとDBリースで排他する。従来のPython取得器を再利用し、要求間隔2秒・直列・403/429停止を維持する。

解析データ、履歴、取得計画とカーソル、条件、gzip原本と取得メタデータを外部PostgreSQLへ保存する。原本はSHA-256で重複排除し、展開後も検証する。一時ファイルは取得器への入力キャッシュのみで、消えてもDBから復元する。訂正時は旧スナップショットを残して最新ポインタを切り替え、保存条件は保存時の版で再現する。

無料枠に対して原本の圧縮合計350MB、原本追加時のDB使用量750MBを初期停止基準とする。これらはNeon Freeの候補容量に余裕を取るアプリ側基準であり、提供元のハード上限・転送/実行時間上限の確認を置き換えない。全1,291開催と補助結果の収容は未実証。容量を理由に旧原本を削除したり有料化したりしない。Object Storageへの分離・追加バックアップ先は未実装で、0円維持を確認してから決める。

Render Freeの候補設定はルートの `render.yaml`。Render Free Postgresは30日で期限切れのため使わない。無アクセス時休止を初回データ準備の中断と結び付け、通常利用の重大な障害として確認を繰り返さない。

SitesをWeb画面の配備候補として確認した。Sitesのサーバー実行はCloudflare WorkerのJavaScriptで、HTTP接続と128MBの実行環境が前提となる。既存Python CLIをそのまま常駐させる構成にはせず、利用する場合はPython API・取得ワーカーを対応する別環境に置き、HTTPSで連携する等の適合確認が必要。別のPython対応Webホストと運用費・構成の負担を比較し、ここでは配備先を確定しない。

利用者のPC内DB、画面サーバーの一時ファイル、現在のCodex環境の `work/` は本番の永続保存先にしない。DBと原本は再デプロイ・再起動後も残し、開発・検証・本番を分ける。

## 4. 取得ジョブとWeb操作

- 「データを取得」「オッズを更新」はAPIからジョブを登録し、ジョブIDと状態を返す。長時間収集を画面のHTTP応答中に完走させない。
- ジョブの対象・進捗・成功/失敗・再開位置は永続保存する。タブを閉じたり画面を再読み込みしたりしても状態を確認できる。
- 既定の要求間隔・回数制限、403/429での停止、原本再利用、取得・解析の版別保存を維持する。複数の更新操作やワーカー再起動でも二重取得と過剰な並列通信を防ぐ。
- ユーザー指定に従い、収集ボタンからだけJRA取得を開始する。通常の検索・条件変更・再読込・条件保存・CSVはDBだけを参照する。画面を開いている間のジョブ状態照会はDBへの問い合わせで、JRA通信ではない。
- 失敗時は最後の成功版・取得時刻と失敗状態を表示する。未取得・未発売・不明・不的中を区別する。

### 収集ボタンと無料Webの休止

「最新データを収集」は前年・当年の一覧を更新し、未保存の開催と開催後14日以内の保存済み結果・確定オッズを取得する。古い開催の訂正は範囲を指定した再取得で扱う。「過去データを収集」は指定期間の未保存開催を取得する。再開はDBに固定した計画とカーソルを使い、再読込だけで取得を勝手に再開しない。

Renderの15分休止は利用者からWebサーバーへのアクセスがないときの仕様で、DBに保管済みかどうかとは独立する。候補構成では次のアクセス時にサーバーを起動し、外部DBのデータを読み出す。収集中に画面を閉じて休止・再起動した場合は、最後の保存済み開催の次から「再開」で続ける。ユーザーの指摘により、長時間となり得る初回の全履歴整備は開発側の公開準備として分離する。過去分と直近までをDBへ用意した後、利用時は保存済みDBを検索し、収集ボタンでは新規・変更分を取得する。毎回10年分を再取得しない。休止による初回準備中断の可能性を、通常利用の構成を決める重大な懸念や追加の承諾待ちとして扱わない。差分更新の実時間は公開前に測定し、収集中断後の再開は維持する。

## 5. Web化で追加する完了条件

以下を機能1と機能2の段階に分けて確認する。機能1の完成提示には、対象履歴の整備と独立した過去分析の稼働が必要。取得CLIの合格や代表サンプルだけの画面表示は完成確認に置き換えない。

1. 検証用URLから画面とAPIを利用でき、利用者のPCでプロセスを起動しなくてよい。
2. 実際のAPI/ワーカー配備候補からJRAのHTTPS・通常フォーム送信と少量取得を確認する。Codex環境で成功した事実だけで本番の接続成功としない。
3. DB・原本・ジョブ・条件が再デプロイ後も残り、ジョブを重複なく再開できる。
4. 更新操作の連打・再読込・失敗・再起動でも、以前の成功データと証跡を失わない。
5. 採用した公開範囲に応じてアクセスを制御し、取得・管理操作を保護する。秘密情報をブラウザに渡さない。
6. 検索・照合・期待値・情報時点を、APIテストとブラウザの一連操作で確認する。
7. DBと原本を別の検証環境へ復元し、集計結果を再現する。本番更新・切戻し・失敗ジョブ確認の手順を整える。

## 6. 次の進め方

主要規則と過去分析の画面/API・永続保存・取得ジョブは実装し、内部で実原本・PostgreSQL・ブラウザを検証した。次は無料配備先の接続と動作条件を確定し、外部HTTPS URL・配備先からのJRA取得・再起動/復元を確認する。全対象の収集・欠損・容量と速度を確認し、作業9で利用URLと検証結果をユーザーへ提示して機能1の完成を確認する。

その確認を記録した後に作業10〜11で今回データ・条件適用・期待値を追加し、12〜13で両機能を同時に確認できる連携と本番運用を仕上げる。[実装計画v3.2](implementation_plan.md) の新しい番号を適用する。現在、機能1の完成確認は未実施。

既存の取得CLIは開発・検証とワーカー組み込みのために維持する。内部検証を、公開先での運用成立や機能1のユーザー完成確認の代替とはしない。[配備・運用手順](web_operations.md) を参照。
