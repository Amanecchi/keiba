# 競馬データ分析ツール 基本設計書

版：3.1 / 更新日：2026-11-07 / 状態：機能1先行。JRA平地重賞全体・本人限定・運用費無料をユーザーが指定

## 1. 目的と確定事項

次の2つを別機能として作る。**機能1を独立したWeb機能として完成させ、ユーザーが完成を確認してから機能2の開発に進む。** 最終版では両機能を同じWebシステムで同時に利用・参照できるようにする。

1. **過去分析**：過去のレースデータを収集・保存し、指定条件で検索・集計・比較表示する。今回のレース選択、出馬表、発売中オッズを入力しなくても利用できる。
2. **今回への適用**：機能1で設定した条件と過去分析の結果を今回の出走馬へ適用し、一致状況、単複の期待払戻・期待収支・回収率の目安を表示する。

過去分析は単独の目的を持ち、機能2の準備画面としてだけは扱わない。機械学習や選択していない要素による独自補正は加えない。

最新のユーザー指定を優先し、添付の開発方針を仕様の基礎とする。

11/7の追加指定により、最終成果物はサーバー上で動作し、URLから利用するWebシステムとする。利用者のPCでPython・取得CLI・DBを起動する手順は製品要件から外す。既存の取得コード・実証・分析計算の方針は引き継ぐ。[Web構成・配備方針](web_architecture.md) を参照。

| 項目 | 設計方針 |
| --- | --- |
| 利用環境 | Web上で動作し、ブラウザからURLへアクセス。取得・保存・分析はサーバー側で実行 |
| 公開範囲 | ご本人だけがログインして利用。画面・API・データ取得/管理操作のすべてを本人限定にする |
| 最終対象 | 機能1の初版はJRA平地重賞全体の最低10年以上。障害・地方・海外は後の拡張対象 |
| 運用費 | データ取得だけでなく、Webサーバー・DB・原本/バックアップ保存等も無料に限定。有料契約・自動課金への切替は採用しない |
| 取得元・代表レース | ユーザー指定でJRA公式に確定。代表レース案はアルゼンチン共和国杯。PDF解析・有料サービスは不採用 |
| データ更新 | 初回の過去データ収集、履歴の差分更新、指定した次走の出馬表・オッズの随時取得 |
| 券種 | 単勝・複勝。連系馬券・購入機能は今回の対象外 |
| 主要画面 | 過去の傾向、今回の出走馬、データ管理 |
| 開発順序 | 機能1の単独完成 → Webでのユーザー完成確認 → 機能2 → 両機能の同時利用・連携 |

取得元はJRA公式に確定。過去結果・払戻・走歴は公式HTMLを中心とし、日程ICSは補助候補。有料データサービス、PDF文字抽出・OCRや高コストの補完は採用しない。運用費は無料に限定し、無料枠の容量・通信・CPU・取得時間と、超過時の停止を確認する。無料枠を超えた場合は新規取得等を停止して既存データを保持し、有料化で解決しない。10年以上の対象履歴・証跡・復元を含めた成立性は実測して判断する。

## 2. 対象範囲と期間

ユーザーの確認回答により、機能1の最初の完成範囲はJRA平地重賞全体に確定した。過去の中央Jpn表記も開催主催と当時区分で判定し、G表記だけに絞らない。障害重賞・地方・海外の重賞は後の拡張対象であり、初版の分析対象とは分けて明示する。前走・脚質の判定に必要な一般戦等の補助走歴は取得対象に含めるが、平地重賞の集計分母へ混ぜない。対象の区分は設定で保持し、拡張時に集計ロジックを書き直さない。

保持する履歴は最低10年以上とし、15/20年への拡張は負担を比較して決める。機能1ではレース系列と任意の過去の日付範囲を直接指定し、開始日・終了日を表示する。今回の発走日時を検索の必須入力にしない。

機能2で今回の発走日時DからN年を遡る場合は、DのN年前の同日以上、D未満を使い、対応日がなければ2月28日を採用する。機能1の保存済み期間や母集団を暗黙に書き換えず、適用する期間・条件・版を明示する。レースの格付けは開催当時の値を保持する。検索対象の格付けと、同一系列の改称・格付け変更を含めるかは別設定にする。

前走や脚質を求めるため、集計対象外の一般戦・期間の開始日より前の走歴も必要な範囲で取得する。補助走歴を重賞の集計分母に混ぜない。

## 3. 技術構成

ブラウザのWeb画面、分析・検索API、永続DB、原本の永続ストレージ、取得ワーカーに分離する。既存のPython 3.12の取得・解析処理と83件のテストを再利用し、Python API・ワーカーとWebフロントを組み合わせる構成を第一候補とする。APIフレームワーク、画面フレームワーク、DB・配備サービスは、対応ランタイム・費用・ジョブ時間・永続容量を比較して選定する。

本番DBはサーバー上の永続RDBを用いる。PostgreSQL等を候補とし、原本とバックアップは永続ストレージへ保存する。従来案のStreamlit・PC内SQLite・127.0.0.1待受は最終成果物の確定構成から外す。SQLAlchemy・Alembic等は選定したPython/DB構成に適合する場合に採用する。JRAはサーバー側から取得し、ブラウザはアプリのAPIを呼ぶ。

データ取得は取得元に合わせたHTTPクライアントと専用アダプターに分離する。外部サービス依存を集計・画面へ持ち込まない。JRA公式HTMLと、低コストで利用できる場合の公式ICSに合わせて取得側を分離する。PDF/OCR・JV-Linkを依存に加えない。ブラウザ自動操作が必要な場合は工数を比較して採否を決める。

処理の流れ：JRA公式 → サーバーの取得ジョブ → 原本の永続保存 → 解析・正規化・検査 → 永続DB → 分析API → Web画面。

| 層 | 責務 |
| --- | --- |
| collectors / workers | サーバー側で過去開催・今後の日程・出馬表・結果・払戻・オッズを取得。ジョブを再開可能にする |
| ingestion | 原本解析、ID対応付け、重複排除、更新、品質検査 |
| domain | 条件定義、発走前の情報選択、集計、期待値計算 |
| storage | 永続DB・原本保存、移行、検索、バックアップ |
| api | 検索・集計・条件照合、取得ジョブの登録と状態取得、アクセス制御 |
| ui | URLから利用する条件入力、表・明細、取得操作、進捗・エラー表示 |

検証用URLを早期に用意し、本番はHTTPSで利用する。利用者はブラウザを使い、環境構築・取得コマンドの実行・DB起動を必要としない。開発・検証と本番の環境・データを分け、秘密情報はサーバー設定で管理し、DB・原本とともにGit管理しない。開発用CLIは取得ワーカーへ組み込むための検証手段として残す。

## 4. データ収集・更新

### 4.1 取得元調査

JRA公式の最低10年以上の対象開催一覧、結果、馬ID、前走・過去走、確定払戻、今後の日程、出馬表、単複オッズと取得時刻を確認する。非HTML形式の再調査は [公式形式調査](jra_official_formats.md) を参照。netkeiba等は過去の比較候補であり、実装の取得元にはしない。

JRA公式内の必要項目と提供項目の対応表を作り、使用する画面・ファイルを確定する。公式内で画面ごとに識別子が違う場合も対応を管理し、馬名だけで自動結合しない。取得できない項目は利用不可と表示し、推測値を補わない。取得元の仕様・利用条件に合う取得方法を採用する。

ユーザー指定により、この調査の実取得は [自動取得検証ツール](acquisition_probe.md) で行う。機能1は過去データの自動取得と負担の確認を開始条件とし、今回の出馬表・発売中オッズの利用可能性に依存させない。既存の次走取得実証は成果として保持し、機能2の段階で利用・再確認する。自動取得が成立しない場合は方式比較へ戻り、理由とコストを提示してユーザーが変更先を選ぶ。環境制限と提供元の取得可否を区別する。

### 4.2 実行方法

- 過去一括取得：期間・区分を指定。開催一覧から必要な出走・補助走歴・払戻を取得する。
- 差分更新：新規開催、未完了データ、訂正対象を取得する。再取得範囲も指定可能にする。
- 次走取得：「今後のレースを更新」で日程を取得し、レース選択後に出馬表・必要な過去走を取得する。
- オッズ更新：「最新オッズを取得」で単複オッズを更新する。自動高頻度ポーリングは初版に含めない。
- 結果確定後：今回のレースを過去データとして更新し、出馬表取得時の記録とオッズ履歴は保持する。

更新操作はサーバーのジョブを登録し、画面にはジョブID・進捗・成功/失敗件数を返す。長い取得処理を画面のHTTP応答中に完走させない。ブラウザを閉じてもジョブ状態と取得済み原本が残り、再表示で同じジョブを確認できるようにする。画面の再描画では取得を実行しない。初版は取得先への実行を直列に制御し、複数のボタン操作やサーバー再起動でも重複ジョブと同時アクセスを防ぐ。保存は短いトランザクションに区切る。

### 4.3 信頼性

提供元・取得日時・提供元が示す更新日時・対象ID・原本ハッシュ・解析バージョンを記録する。原本を保存して再解析を可能にする。タイムアウトと一時障害には回数制限付きで再試行し、指定頻度を守る。認証失敗・形式変更・検査不合格は失敗として残し、正常データを上書きしない。途中から再開できる単位は開催および取得リソースとする。

## 5. データモデル

| データ | 主な内容・制約 |
| --- | --- |
| race_series | 改称・開催場変更を含む同一レース系列。名称だけで結合せず対応履歴を保持 |
| races | 開催日時、競馬場、レース番号、系列、当時の格付け、芝ダート、距離、状態 |
| horses / participants | 馬、騎手、種牡馬、所属のIDと提供元ID対応 |
| entries | レースID＋馬IDを一意にし、枠・馬番・性齢・騎手・所属・着順・取消等の状態を保存 |
| entry_features | 出走当時の前走参照、脚質、レース間隔、算出方式・版、根拠走歴、情報の判定時点 |
| payouts | レース・券種・対象馬ごとの100円払戻、返還状態、確定・欠損の区別 |
| odds_snapshots | 出走・券種・倍率または上下限・人気・取得日時・提供時刻。確定オッズも別種別で保存 |
| source_records | 提供元ID対応、原本パス、取得・提供日時、解析版 |
| import_jobs / coverage | 取得対象、進捗、成功・失敗、再開位置、期待件数・取得件数・欠損理由 |
| saved_conditions | 条件、分類軸、期間、系列・区分設定、仕様版 |

日時はUTCで保存し、画面は日本時間を明記する。金額は整数円、倍率と率はDecimal等で扱い、丸めは表示時だけ行う。率・倍率の既定表示は小数1桁、期待金額は1円単位で四捨五入する。

0・不的中・未取得・提供なし・未確定を区別する。結果や払戻の訂正を追跡できる履歴を残し、分析条件・使用データ版を記録して計算根拠をたどれるようにする。

## 6. 検索条件と集計対象

初版の条件は枠順、脚質、騎手、種牡馬、性齢、所属、前走クラス、前走距離、レース間隔、人気、前走レース名、前走着順、単勝オッズ帯。年・期間・競馬場・対象レース系列で母集団を決める。

条件間はAND、同一項目の複数選択はOR。数値範囲は上下限を含む。未指定項目は判定に使わない。条件値が欠損した場合は不明とし、一致に含めず、不一致とは別の件数を表示する。フィルターと分類軸は独立し、分類不能は「不明」グループにする。

前走は対象レースより前の直近実出走とし、取消・除外は飛ばす。前走クラスは当時の公式競走条件・格付けを使い、旧条件名と現行クラスの対応および原表記を保持する。脚質は対象日前の直近3実出走の最初の通過順位を頭数で正規化し、有効な2走以上で分類する。[分析規則v0.2](analysis_rules.md) に根拠・閾値・方式版を定義した。分類不能は不明とし、今回の結果や将来走歴は使わない。

履歴の人気・オッズ条件は確定値を使うモードと、指定時点の記録を使うモードを区別する。今回の条件照合は取得時点の値を使用する。確定値しかない履歴から算出した目安は、その差を明示する。時点をそろえられない条件は厳密な過去再現の検証対象から外し、検証不能理由を残す。

## 7. 集計ルール

集計単位は「ある開催における1頭の出走」。複数年に同じ馬が出た場合は別出走とする。条件一致件数、実出走数、結果未確定数、払戻確認済み数を分けて返す。

| 指標 | 定義 |
| --- | --- |
| 勝率 | 1着出走数 ÷ 結果確定済み実出走数 |
| 連対率 | 2着以内出走数 ÷ 同分母 |
| 複勝率（3着以内率） | 3着以内出走数 ÷ 同分母 |
| 複勝的中率 | 実際の複勝払戻対象出走数 ÷ 複勝的中判定済みの有効出走数 |
| 実績回収率 | 各券種の確定払戻総額 ÷ 有効購入総額 × 100 |

取消・除外・全額返還は、その券種の有効購入額・回収率分子・分母から除外する。実出走したが競走中止・失格となった馬は結果確定後の実出走分母に含め、確定払戻に従う。全額返還と実出走率の分母は別判定とする。同着は公式着順と確定払戻を採用する。

各券種100円均等購入とする。払戻未取得を0円にしない。回収率は払戻確認済みの有効出走で計算し、その対象件数と欠損件数を併記する。率ごとの分母が異なる場合は列ごとに明示する。該当0件は算出不可、0勝8頭は0/8・0%とする。条件を自動で緩めない。

標本数30未満は「参考件数が少ない」と表示する。30は表示用の基準であり信頼性の保証ではない。自動的な確率補正はしない。

## 8. 今回のレースと期待値

本節は機能2の仕様。機能1の完成をユーザーが確認した後に実装する。機能1の履歴検索・集計・比較は、この機能を使用しなくても動作する。

画面の既定の母集団は、今回と同じレース系列の、対象発走日時より前の対象期間内開催。同じ条件セットを今回の各馬に照合し、一致・不一致・情報不足を表示する。一致した各馬には同じ条件母集団の率を用いる。馬ごとに隠れた補正や別条件を生成しない。絞り込みを変えると根拠明細と全表示を再計算する。

勝率p、単勝倍率o、購入額bに対して以下を表示する。

- 回収率の目安：p × o × 100%。
- 期待払戻：b × p × o 円。
- 期待収支：b × (p × o − 1) 円。

p=0.10、o=12.0、b=100なら120%、120円、+20円。過去の実績回収率とは別列にする。複勝は実際の複勝的中率qと今回倍率の上下限を使い、同様の式で概算範囲を示す。3着以内率を代用しない。

オッズ未発売・欠損、母集団0件、今回の条件判定不能、取消・除外では該当する期待値を算出しない。過去0勝は0%として表示する。取得時刻・提供時刻・経過時間を常時示し、10分超を暫定の古いデータ表示基準とする。古くても無断で最新扱いせず、更新操作を案内する。

## 9. 画面

### 過去の傾向

レース系列・期間・区分・競馬場を選択 → 条件を追加 → 分類軸を選択 → 集計表と明細を表示。明細には年、馬名、前走、前走着順、本番着順、払戻を含める。表と明細は同じ検索結果から作り、件数を一致させる。条件の保存・再読込、表示結果のCSV出力を用意する。

この画面へ直接アクセスでき、今回のレースを選ばず完結する。対象履歴・必要条件の整備、計算・明細の一致、Web上の一連操作をそろえて、機能1の完成確認に提示する。代表サンプルの表示だけを完成扱いにしない。

### 今回の出走馬

今後の日程更新 → レース選択 → 出馬表取得 → 条件読込・変更 → 単複オッズ更新 → 一致状況と期待値表示。枠順等の未発表項目は情報不足として示す。各馬から過去の根拠明細を開けるようにする。取得失敗時は前回データとその時刻を保持し、最新取得失敗を表示する。

機能1の保存条件と分析結果を参照し、過去の分析結果と今回の適用結果を同時に確認できる表示・連携を用意する。機能1の独立した入口も残す。今回のオッズ更新で変わるのは今回の概算であり、同じ保存済み過去データの実績集計は変えない。

### データ管理

取得期間・区分の選択、初回収集・差分更新・再取得、進捗、失敗の再実行、年別の網羅率、未対応項目、バックアップ・復元を提供する。データ未取得を「該当なし」と誤認させない。

## 10. 検証・性能・運用

機能1の完成確認では、Web上の独立した過去検索、合意した対象範囲の最低10年以上のデータ、条件別集計・根拠明細・保存/再読込、欠損/取消等の検査、継続利用の保存・復元を確認する。操作できるURL・取得範囲・検証結果をユーザーへ提示し、完成確認を記録する。自動テストや取得CLIの合格を、その完成確認の代わりにしない。確認前は機能2の本体実装へ進まない。

既存の tests/analysis_test_cases.md を受け入れ仕様の起点とし、本設計で定めた返還・欠損・同着・時点のケースを追加して自動化する。純粋計算、取得原本の解析、DB再取り込み、画面の一連の操作を段階的に検証する。日常の自動テストはネットワーク接続なしで実行できるようにする。

過去開催の再現では、その開催以前の履歴だけを集計し、当時利用可能な情報のみで条件を判定する。履歴のオッズ時点がない場合は厳密な当時の期待値検証ができないことを明記し、確定オッズで検証できたことに置き換えない。

全対象の取得完了は開催一覧との突合で判定する。失敗・不足を含む場合は未完了とする。網羅率の分母となる開催一覧自体の欠落も、年別公表開催数など独立した情報で照合する。

性能目標は、採用した10年以上の対象データに対する通常の検索・集計がWeb画面からの操作で概ね3秒以内。ブラウザの表示完了までとAPI処理時間を分け、配備環境・通信条件・件数・コールド/ウォームを記録して測定する。取得ジョブの完了時間は別計測とする。

依存版を固定し、DB移行・本番更新前にバックアップする。バックアップは永続DB・原本・保存条件・提供元対応を対象とし、別の検証環境へ復元して分析結果を照合する。再デプロイやワーカー再起動でデータを失わないことも検証する。認証情報はサーバーの環境変数・秘密情報設定で管理し、ブラウザやログへ出さない。

## 11. 調査で確定する事項

JRA公式内の取得形式・画面、平地重賞全体の最低10年以上の網羅性、脚質の方式、過去オッズの時点精度、欠損項目、無料Web配備先と永続容量を調査・検証記録で確定する。対象範囲・本人限定・運用費無料は確定事項。配備候補からのJRA接続も少量実証し、Codexでの成功と区別する。それ以外は本書の既定で実装し、変更時は理由と影響ケースを残す。
