# 過去分析Webの配備・運用

更新：2026-11-07 / v0.5.0 / 外部サービスには未配備。以下の配備作業は開発担当者が行い、利用者のPCでのコマンド実行を前提にしない。

## 利用者の操作

1. 配備後に案内するHTTPS URLへアクセスする。初回だけ、配備先の管理画面で発行された本人用の初期設定コードを使い、ブラウザでパスワードを設定する。以後はログイン名 `owner` と設定したパスワードで入る。コード・パスワードをチャットへ貼らない。
2. 「データ収集」で対象レース・年度を選び「過去データを収集」。最新情報は「最新データを収集」から取得する。通常検索は保存済みDBだけを使用する。
3. レース・期間・条件・分類軸を指定し「保存データで分析」。明細は25件ずつ表示する。CSVは表示対象の全件を保存する。
4. 「この条件を保存」は条件とデータ版を保存する。読込時は訂正前を含む保存時点を再現し、「現在の保存データで再分析」で最新DBへ切り替える。この操作でもJRAへ通信しない。
5. 収集が停止した場合は理由を確認する。再開は同じ計画の未完了開催から行う。403/429等は先方・実行環境の状態を確認してから再開し、連打や制限回避をしない。

「最新」は前年・当年の一覧、新規開催と開催後14日以内の保存済み結果/確定オッズを対象とする。もっと古い結果の訂正は対象年度を指定し「保存済み原本も再取得」を使う。分析期間は指定したままなので、今回収集した日付が期間外なら終了日を変更する。

## 外部配備前に残る条件

- Render/Neonは候補。追加・アカウント接続、無料プランの実アカウント条件を確認する。接続用秘密情報は環境の秘密設定を使い、Gitやチャットに保存しない。
- 本人限定・Web/DB/原本/バックアップ/転送すべて0円に限定する。カード登録、試用クレジット終了後の有料化、自動課金で補わない。無料枠超過時の停止・既存データ保持を確認する。
- Render Freeの15分無アクセス時休止は未承諾。DB永続化とは別の動作条件として説明し、採用を確定する。休止しない無料ホストが必要な場合は代替を調べる。
- 本番からJRAへHTTPS/公開フォームの少量取得、再デプロイ後の永続保存・ジョブ再開、別DBへの復元を確認する。Codex内での成功を本番検証として扱わない。

## 開発担当者向け配備設定

[`render.yaml`](../render.yaml) はPython 3.12.12、Free Web、1プロセス・4スレッド、HTTPS終端、`/healthz` を想定する。Renderの期限付き無料Postgresは使わず、期限のない外部無料PostgreSQLのURLを秘密設定へ登録する。Renderのビルド定義を適用する前に、実際に全設定が無料サービスを指していることを確認する。

| 環境変数 | 内容 |
| --- | --- |
| `DATABASE_URL` | 永続PostgreSQL。Neonの管理画面が発行するTLS付きURLを想定。アプリは一時DBへ代替しない |
| `KEIBA_SESSION_SECRET` | 32文字以上のランダム値。Blueprintで生成。維持すれば再配備後もセッション署名を継続 |
| `KEIBA_OWNER_SETUP_TOKEN` | 32文字以上のランダム初期設定コード。Blueprintで生成。初期設定完了後は使用不可、環境変数から削除可能 |
| `KEIBA_OWNER_NAME` | 初期値 `owner`。変更時は利用者へ案内 |
| `KEIBA_OWNER_PASSWORD_HASH` | 通常は未設定。管理担当者による明示的なログイン復旧時だけ、Werkzeug形式のハッシュで上書き可能。平文パスワードを設定しない |
| `RENDER_EXTERNAL_HOSTNAME` | Renderが設定するサービスのホスト名。別ホストでは `KEIBA_ALLOWED_HOSTS` を明示 |

ログイン設定はDBにハッシュだけを保存する。初期設定後に `/setup` から上書きできない。ログイン・初期設定・取得・検索POSTはCSRF/Origin検査を行う。CookieはSecure/HttpOnly/SameSite Strict。本番は既定の利用者パスワードを持たない。

配備後、初期設定→ログイン→代表1開催の収集→集計→条件保存→CSV→再デプロイ→同じデータ版/原本ハッシュ/ジョブ位置の再確認を行う。新しい版は自動配備せず、チェック後に配備する。機能2は機能1のユーザー完成確認後に追加する。

## DB・原本と無料枠

初期スキーマは `keiba_settings`、`source_blobs`、`source_fetches`、`race_catalog`、`catalog_runs`、`analysis_races`、`analysis_snapshots`、`saved_searches`、`acquisition_jobs`。スキーマ版1を起動時に確認する。初期作成は非破壊、既存列の変更・削除は自動で行わない。将来のスキーマ変更は移行・バックアップ・復元検証を作成してから配備する。

原本はgzip・SHA-256で格納。圧縮原本350MB、原本追加時のPostgreSQLサイズ750MBを停止基準とし、元の原本・旧解析版を削除しない。DB提供元の容量/実行時間/転送上限も別に適用される。全平地重賞10年と補助走歴の容量は未実測で、収容できるという約束はしない。停止時は容量内の無料代替案を検討する。

収集計画・カーソルと120秒の排他リースはDB保存。アプリ再起動だけでJRA取得を自動再開せず、画面の「再開」で実行する。途中の開催は保存済み原本を再利用して再試行し、以前に成功した開催は再計上しない。画面の状態照会はDBの読込である。

## バックアップ・復元・切戻し

内部検証ではPostgreSQL 17の `pg_dump --format=custom` でDB全体を取得し、別の空DBへ `pg_restore --no-owner --exit-on-error`。同じデータ版・159出走・全指標と原本301件のハッシュ一致を確認した。これは検証用DBでの実証であり、クラウドの定期バックアップは未設定。

本番は配備・大規模収集・スキーマ変更前に整合したDB全体のバックアップを作り、原本・旧版・保存条件・ジョブ・ログイン設定も含める。復元は隔離した空DBへ行い、件数、原本ハッシュ、データ版、代表集計、本人ログイン、未完了ジョブの再開を確認してから接続先を切り替える。バックアップはログインハッシュ等を含むため非公開で保管する。実際の無料保存先・容量・保持期間・別環境復元を確認するまでは運用完了にしない。

アプリの切戻しは検証済みコミットを再配備する。DBの旧解析スナップショットは保持する。互換性のないDBへ旧コードを接続せず、対応するスキーマ版か復元DBを使用する。
